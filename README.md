## ⚠️ قبل از هر چیز

این یک ابزار مهندسی‌شده است، نه یک ماشین پول‌سازی. سه نکته‌ای که باید بپذیری:

1. **هیچ ربات معامله‌گری سود تضمینی ندارد.** این کد تصمیم‌گیری را منظم و بدون احساسات می‌کند؛ «لبه‌ی بازار» (edge) را از هوا نمی‌سازد.
2. **این استراتژی روی داده‌ی واقعی ضرر می‌دهد.** این حدس نیست — سنجیده‌ایم، سه بار.
   روی ۱۶ سال EURUSD و با تست walk-forward، بازده خارج از نمونه **‎−۲۰.۷۵٪** بود.
   بهترین ترکیبی که با روش پیش‌ثبت‌شده پیدا شد روی داده‌ی دست‌نخورده ‎+۱.۱۷٪ در
   ۱۵ ماه داد — ولی با p = ۰.۴۵. بعد همان قانونِ منجمد روی **شش جفت ارزی که در هیچ
   تصمیمی استفاده نشده بودند** اجرا شد: ۲٬۷۱۷ معامله، انتظارِ وزن‌دار با ریسک
   **‎−۰.۰۱R**. یعنی صفر. عدد به عدد در **[`BACKTEST.md`](BACKTEST.md)**.
   اول آن را بخوانید.
   
   آزمایش چهارم ریشه‌ی ماجرا را پیدا کرد و آن یک **باگ در خود ابزار اندازه‌گیری**
   بود: پوزیشنی که سود جزئی می‌گیرد *دو* رکورد می‌نویسد (هر دو برنده) و پوزیشنی که
   به حد ضرر می‌خورد *یک* رکورد. پس برنده‌ها دو بار شمرده می‌شدند. ‎۶.۶٪‎ از
   پوزیشن‌ها سود جزئی گرفتند و همان‌ها ‎۸۶٪‎ از «لبه»ی ظاهری را می‌ساختند. با
   اندازه‌گیری درست: **‎+۰.۱۱۱R‎ ← ‎+۰.۰۱۶R‎** و ‎t=۶.۳۱ ← t=۰.۹۱‎. یعنی هیچ.
   موتور حالا بر پایه‌ی *پوزیشن* گزارش می‌دهد و رقم سوگیرانه را هم کنارش
   نشان می‌دهد تا اندازه‌ی خطا دیده شود.
3. **ارزش این مخزن، ماشین سنجش صادقانه‌اش است، نه استراتژی‌اش.** زیرساخت (بدون نگاه به
   آینده، شبیه‌سازی واقع‌گرایانه‌ی هزینه‌ها، مدیریت ریسک، walk-forward) تست‌شده و قابل اتکاست.
   استراتژی خودتان را رویش سوار کنید.
4. **مسیر درست:** بک‌تست ← walk-forward ← پیپر حداقل ۱ تا ۳ ماه ← حساب دمو ← حساب واقعی کوچک.
   حالت لایو عمداً پشت دو قفل است.
5. **برای معامله‌ی واقعی به ویندوز نیاز دارید** (ترمینال MT5 فقط ویندوزی است).
   هاست اشتراکی cPanel کار نمی‌کند. برای نصب روی **ویندوز شخصی** به صورت یک
   نرم‌افزار معمولی → **[`WINDOWS.md`](WINDOWS.md)**. برای سرور/VPS →
   **[`DEPLOYMENT.md`](DEPLOYMENT.md)**.

## ۳. موتور تصمیم‌گیری

شش «بلوک رأی‌دهنده» مستقل، هر کدام بازار را در بازه‌ی `[-1, +1]` امتیاز می‌دهند:

| بلوک | چه می‌خواند | وزن پایه |
|---|---|---|
| `trend` | EMA 21/55/200، ADX و ±DI، Supertrend، Parabolic SAR، شیب رگرسیون خطی | ۱٫۰۰ |
| `momentum` | RSI، Stochastic، MACD، CCI، ROC، Williams %R، واگرایی RSI | ۰٫۹۰ |
| `volatility` | Bollinger %B، شکست Keltner، Squeeze، صدک ATR | ۰٫۶۰ |
| `volume` | MFI، Chaikin Money Flow، شیب OBV، Force Index، حجم نسبی | ۰٫۵۰ |
| `structure` | ساختار سوئینگ‌ها، شکست Donchian، عمق پولبک، الگوی کندل | ۰٫۸۰ |
| `htf_bias` | همین تحلیل روی تایم‌فریم بالاتر (پیش‌فرض H4) | ۱٫۰۰ |

### نکته‌ی کلیدی: وزن‌ها ثابت نیستند

سیستم اول **رژیم بازار** را تشخیص می‌دهد (`TREND_UP`، `TREND_DOWN`، `RANGE`، `VOLATILE`، `QUIET`) و بعد وزن‌ها را بازتنظیم می‌کند:

- در **روند**: بلوک trend ×۱٫۳۵، نوسان‌نماها ساکت‌تر، و اسیلاتورها **هم‌جهت روند** خوانده می‌شوند.
- در **رِنج**: بلوک momentum ×۱٫۳، و همان اسیلاتورها **برعکس** تفسیر می‌شوند (RSI بالای ۷۰ یعنی سیگنال فروش، نه خرید).

این تفاوت بین یک ربات حرفه‌ای و یک «EMA cross» ساده است.

### شرایط ورود

معامله فقط وقتی باز می‌شود که **همه‌ی** این‌ها برقرار باشد:

</div>

```
|score| ≥ entry_threshold            (پیش‌فرض ۰٫۲۸)
confidence ≥ min_confidence          (پیش‌فرض ۰٫۴۵)
تعداد بلوک‌های هم‌نظر ≥ 3
تایم‌فریم بالاتر مخالف نباشد
داخل سشن معاملاتی مجاز
اسپرد زیر سقف تعیین‌شده
هیچ وتوی مدیریت ریسک فعال نباشد
```

## ۴. مدیریت ریسک

مهم‌ترین بخش پروژه. **تنظیم درصد ریسک** دقیقاً همان چیزی است که خواستی:

</div>

```yaml
risk:
  risk_per_trade_pct: 1.0      # ◀ درصد اکوئیتی که بین ورود تا حد ضرر ریسک می‌شود
```

<div dir="rtl">

### حجم پوزیشن چطور حساب می‌شود؟

حجم **مشتق** می‌شود، حدس زده نمی‌شود:

</div>

```
پول در معرض ریسک = اکوئیتی × risk_per_trade_pct / 100
ضرر هر لات       = فاصله‌ی حد ضرر / tick_size × tick_value
حجم (lot)        = پول در معرض ریسک / (ضرر هر لات + کمیسیون)
```

<div dir="rtl">

یعنی حد ضرر پهن → حجم کوچک، حد ضرر تنگ → حجم بزرگ، و **پولی که ریسک می‌کنی همیشه ثابت می‌ماند**.

> مثال واقعی از خروجی تست: حساب ۱۰٬۰۰۰ دلار، ریسک ۱٪، حد ضرر ۲۰ پیپ روی EURUSD → دقیقاً **۰٫۵۰ لات** و **۱۰۰ دلار** در معرض ریسک.

### لایه‌های محافظ

| پارامتر | کار |
|---|---|
| `risk_per_trade_pct` | ریسک هر معامله (اهرم اصلی) |
| `scale_risk_with_confidence` | ریسک متناسب با اطمینان سیگنال، بین ×۰٫۵ تا ×۱٫۲۵ |
| `max_total_risk_pct` | سقف مجموع ریسک همه‌ی پوزیشن‌های باز |
| `max_open_positions` / `max_positions_per_symbol` | سقف تعداد پوزیشن |
| `max_currency_exposure` | سقف تمرکز روی یک ارز (مثلاً حداکثر ۲ معامله‌ی درگیر USD) |
| `max_daily_loss_pct` | توقف معاملات تا پایان روز |
| `max_weekly_loss_pct` | توقف تا پایان هفته |
| `max_drawdown_pct` | **کلید قطع اضطراری** از سقف اکوئیتی |
| `max_consecutive_losses` + `cooldown_minutes_after_streak` | استراحت اجباری بعد از ضررهای پیاپی |
| `reduce_risk_after_loss` | کاهش خودکار حجم در دوره‌ی ضرر (پیش‌فرض ×۰٫۶) |
| `min_free_margin_pct` | کف مارجین آزاد |

### مدیریت معامله‌ی باز

- **حد ضرر**: `atr` (ضریبی از ATR) | `fixed_pips` | `structure` (پشت آخرین سوئینگ تأییدشده)
- **سر به سر**: انتقال حد ضرر به نقطه‌ی ورود در `+1R`
- **تریلینگ**: Chandelier روی سقف/کف ثبت‌شده — **فقط به نفع معامله حرکت می‌کند، هرگز شل نمی‌شود**
- **خروج پلکانی**: بستن نصف پوزیشن در `+1.5R`
- **خروج سیگنالی**: وقتی تز معاملاتی تضعیف شد — اما فقط بعد از `+0.6R` سود

</div>

> 💡 چرا `exit_min_r`؟ بدون آن، ربات با هر نوسان کوچکِ امتیاز در سود ناچیز خارج می‌شود و ضررها را کامل می‌خورد — یعنی دقیقاً برعکس «جلوی ضرر را بگیر، بگذار سود بدود».

## ۵. صداقت بک‌تست

بی‌فایده‌ترین چیز دنیا، بک‌تستی است که دروغ می‌گوید. این موتور عمداً بدبین است:

| موضوع | رفتار سیستم |
|---|---|
| زمان پر شدن سفارش | تصمیم روی **بسته‌شدن** کندل، اجرا روی **باز شدن کندل بعدی** |
| اسپرد | خرید روی Ask، فروش روی Bid — رفت و برگشت هزینه دارد |
| اسلیپیج | قابل تنظیم، همیشه **به ضرر** تو |
| کمیسیون | به ازای هر لات، رفت و برگشت |
| سواپ | محاسبه‌ی شبانه، سه‌برابر چهارشنبه‌ها |
| کندل مبهم | اگر کندلی هم حد ضرر و هم حد سود را لمس کرده باشد، **حد ضرر** فرض می‌شود |
| مارجین | سفارش بدون مارجین کافی رد می‌شود (نوشنال جفت‌های پایه‌دلاری درست محاسبه می‌شود) |
| look-ahead | با تست خودکار تضمین شده (پایین را ببین) |
| انتظار (expectancy) | هم میانگین ساده‌ی R و هم **وزن‌دار با ریسک**؛ وقتی اختلاف داشتند، دومی درست است |

### تست طلایی

</div>

```python
# tests/test_engine.py
def test_no_lookahead_future_bars_cannot_change_the_past():
    """دو اجرا از نقطه‌ی یکسان؛ یکی ۶۰۰ کندل آینده را هم می‌بیند.
    هر معامله‌ای که قبل از نقطه‌ی برش بسته شده باید کاملاً یکسان باشد."""
```

<div dir="rtl">

اگر هر اندیکاتور یا قانون اجرایی ذره‌ای به آینده نگاه می‌کرد، این تست می‌شکست.

### ولی بک‌تست سالم هم کافی نیست

یک بک‌تست روی کل تاریخ، **بعد از اینکه پارامترها را دیده‌اید**، تقریباً بی‌معناست.
نشتی دیگر در کد نیست، در خود شماست. راه‌حل، `omega walkforward` است:

</div>

```
|<- ۳۶ ماه بهینه‌سازی ->|<- ۱۲ ماه سنجش ->|
                        |<- ۳۶ ماه بهینه‌سازی ->|<- ۱۲ ماه سنجش ->|
```

```bash
omega walkforward -s EURUSD --set data.source=csv \
  --set data.history_bars=100009 --set strategy.timeframe=H1 \
  --param strategy.entry_threshold=0.28,0.42,0.56 \
  --param risk.atr_stop_mult=2.0,3.0
```

<div dir="rtl">

پارامترها روی پنجره‌ی اول انتخاب و **قفل** می‌شوند، بعد روی پنجره‌ای که بهینه‌ساز هرگز
ندیده اجرا می‌شوند. موجودی حساب از دوره‌ای به دوره‌ی بعد منتقل می‌شود. دو عدد مهم‌تر از
بازده‌اند:

- **Efficiency** = میانه‌ی بازده خارج از نمونه ÷ میانه‌ی داخل نمونه. بالای ۰.۵ سالم است؛
  نزدیک صفر یعنی آنچه دیده‌اید بیش‌برازش بوده.
- **Consistency** = درصد دوره‌هایی که خارج از نمونه سود داده‌اند. ۵۰٪ یعنی شیر یا خط.

نتیجه‌ی واقعی این پروژه روی EURUSD در [`BACKTEST.md`](BACKTEST.md) آمده — با همه‌ی
جزئیات ناخوشایندش، از جمله جایی که خودم در تله‌ی بیش‌برازش افتادم.

## ۱۰.۵ اعلان و کنترل با تلگرام

</div>

```bash
export TELEGRAM_BOT_TOKEN=...   # از @BotFather
export TELEGRAM_CHAT_ID=...     # شناسه‌ی چت خودت
omega notify test               # قبل از اینکه بهش تکیه کنی، تستش کن
```

```yaml
notifications:
  enabled: true
  on_entry: true
  on_exit: true
  on_halt: true            # وقتی نگهبان ریسک ربات را خاموش کرد
  daily_summary_hour: 21   # UTC
  telegram:
    allow_commands: true
    allow_flatten: true    # false = فقط خواندنی
```

<div dir="rtl">

دستورها: `/status`، `/positions`، `/signal`، `/trades`، `/risk 0.5`، `/halt`،
`/resume`، `/flatten`، `/stop`.

سه نکته‌ی طراحی که مهم‌اند:

- **ارسال هرگز حلقه‌ی معاملاتی را بلاک نمی‌کند.** پیام‌ها در یک صف می‌افتند و یک ترد
  جداگانه می‌فرستدشان. اگر تلگرام قطع باشد، شما یک پیام از دست می‌دهید، نه یک پوزیشن.
- **فقط به `chat_id` تنظیم‌شده پاسخ می‌دهد.** پیام هر چت دیگری لاگ و دور انداخته می‌شود.
- **اتصال خروجی است.** هیچ پورتی روی سرور باز نمی‌شود — برخلاف داشبورد.

## ۱۰.۶ امنیت داشبورد

داشبورد `POST /api/control` دارد که می‌تواند **همه‌ی پوزیشن‌ها را ببندد و ریسک را
عوض کند**. اگر روی چیزی جز `127.0.0.1` باز است، حتماً توکن بگذارید:

</div>

```bash
omega dashboard --set dashboard.auth_token=$(python -c "import secrets;print(secrets.token_hex(24))")
```

<div dir="rtl">

بعد یک بار `http://host:8080/?token=...` را باز کنید؛ توکن در کوکی می‌نشیند. کلاینت‌های
API می‌توانند هدر `X-Omega-Token` یا `Authorization: Bearer ...` بفرستند.
اگر توکن نگذارید و host روی `0.0.0.0` باشد، ربات موقع بالا آمدن هشدار می‌دهد.

امن‌ترین کار: داشبورد را روی `127.0.0.1` نگه دارید و از تونل SSH استفاده کنید.
جزئیات کامل در [`DEPLOYMENT.md`](DEPLOYMENT.md).

## ۱۱. تنظیم برای بازار خودت

| هدف | چه کنی |
|---|---|
| معاملات کمتر ولی با کیفیت بالاتر | `entry_threshold` ↑ ، `min_agreeing_blocks` را ۴ کن |
| ربات زیادی محافظه‌کار است | `entry_threshold` ↓ ، `require_htf_alignment: false` |
| ضررها خیلی بزرگ‌اند | `atr_stop_mult` ↓ یا `risk_per_trade_pct` ↓ |
| سودها خیلی زود بسته می‌شوند | `exit_min_r` ↑ ، `trail_atr_mult` ↑ ، `partial_tp_r` ↑ |
| اسکالپ کوتاه‌مدت | `timeframe: M5` + `htf_timeframe: H1` + اسپرد سخت‌گیرانه |
| سوئینگ بلندمدت | `timeframe: H1` + `htf_timeframe: D1` + `atr_stop_mult: 2.5` |

</div>

> ⚠️ **تله‌ی بهینه‌سازی:** `omega optimize` خیلی راحت پارامترهایی پیدا می‌کند که روی داده‌ی گذشته عالی‌اند و در آینده شکست می‌خورند. همیشه برنده را روی بازه‌ی زمانی‌ای که در بهینه‌سازی نبوده دوباره تست کن.
